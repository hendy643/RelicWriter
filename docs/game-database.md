# The game database

Everything the app knows about the game (not about the save format) is in one SQLite database, managed with Entity Framework Core. The app reads names, perks and enum defaults from it; it does not read the game files for those. The one thing it still reads from the game files is the picture of a vehicle (see below).

## Where it lives

- **The file:** `gamedata.db` in the user's local data folder (`%LOCALAPPDATA%\RelicWriter` on Windows, `~/.local/share/RelicWriter` on Linux; `GameDatabase.UserPath`). It is created on the first start and kept.
- **On every start** the app opens that file and runs the migrations it has not run yet (EF `Migrate()`), then reads all rows into memory (`GameDatabase.Current`) and closes the file. So the file can be replaced or changed while the app runs.
- If the file can't be used (damaged, not writable, or migrated by a newer app) the app uses the built-in data in an in-memory database instead and starts anyway.

## Migrations

- `RelicWriter.Common/GameData/Storage/Migrations/<timestamp>_Schema`, `<timestamp>_LocalData` and any later schema migrations are EF migrations, generated by `dotnet ef` (tables and keys; they are C#, not SQL, so they are not in `Database/`). The tables are the row classes in `GameDbContext.cs`. Schema changes are made the EF way: change the row classes, then `dotnet ef migrations add <Name> --project RelicWriter.Common --startup-project RelicWriter.Common --output-dir GameData/Storage/Migrations` (the tool is in `dotnet-tools.json`; `dotnet tool restore`).
- A **data migration** is a SQL script in the `Database/` folder, `<timestamp>_Game_<game version>.sql`, plus a one-line class `M<timestamp>.cs` next to the schema migration that tells EF about it and runs the script (`SqlScriptMigration`). Both are written by `RelicWriter.Extractor gamedata`. The scripts are compiled into `RelicWriter.Common` as embedded resources.
- A data migration only contains `INSERT OR REPLACE` for rows that are new or changed since the previous data, and **never deletes**. So a database that has run all migrations covers every game version since the first one, and an update is just the new migration, not a whole new database.
- A released migration is never edited. Fix mistakes with a later migration.

## Compatibility

- **Backwards compatible:** a database that has run fewer migrations than the app has is brought up to date by running the missing ones. Saves from old game versions keep resolving because old rows are never deleted.
- **Not forwards compatible:** if the history table holds a migration this app does not have, the file is refused (`DatabaseProblem.TooNew`) and the built-in data is used. A save newer than `MaxSaveVersion` (the newest save version the data was extracted with, `meta.max_save_version`) still opens; the status bar says its names may be missing (`IsOlderThanSave`).
- `DatabaseInfo.DataVersion` is the number of migrations run (schema and data); the game build is `meta.game_version`.

## Tables

`meta` (game_version, max_save_version, created_utc), `enum_default` (type to its first value, what the save leaves out), `record` (TweakDBID hash + name length to record name and in-game display name), `item` (the item catalogue, below), `vehicle` (record, sort, atlas, atlas_part), `perk_tree` (tree to the name of its attribute data in the save), `perk` (id, tree, sort, max_level, cost_per_level, display_name, requires: the perks that must be maxed first, space separated; attribute_points: the attribute value its tier needs), `constant` (for example `official_max_perk_points`), and `local_data`.

**`item`** (hash, length, name, category, type, quality, shape, expansion) is the catalogue the Inventory tab's picker adds from: every record of the seven TweakDB item types that carry in-game text (`ItemTypes` in `GameDataExport`) that has a display name (not "!OBSOLETE") and an item type link, 7,260 in game 2.5. `name` is the in-game name. `category`, `type` and `quality` are the names the record's `.itemCategory`, `.itemType` and `.quality` links point at; TweakDB stores only hashes, so they are found by hashing the known names (`Categories`, `ItemTypeNames`, `Qualities`), and a type the list does not cover is NULL (most cyberware: its type hash is unknown). Recipes (their own record type) are category "Recipe"; the category of a record with no link is "Other". `expansion` is 1 for records that are only in the Phantom Liberty file. `shape` is the `ItemShape` of the save node (0 stack, 1 quantity only, 2 gear): the shape of that item in the given saves where one was seen, else the most common one for its record type and item type. Records that are not obtainable in play (NPC-only variants, vehicle weapons) are not told apart, and there is no "since game version" column, so the catalogue is the 2.5 one. The record table's names win in the inventory view; an item only the catalogue knows takes its name from it (`RecordNames.Display`).

**`local_data`** (key, value) holds the user's own values: the game folder (`game_folder`, remembered by `GameLocator.Remember`) and any later settings, read and written through `LocalData`. It exists in the schema migration only; no data migration writes to it (a test checks this), so an update never touches what the user set. It is not part of the in-memory `GameDatabase` snapshot.

**Vehicle pictures are not in the database.** `vehicle.atlas` is the hash of the texture atlas file's path in the game archives and `atlas_part` the part of it. The app cuts the picture out of the player's own install at run time (`GameIcons`; the archives are decompressed with the game's Oodle DLL on Windows and the managed `Kraken` decoder elsewhere); without the game the tiles show a drawn glyph.

## Making a new migration

```
dotnet run --project RelicWriter.Extractor -- gamedata --game <game dir> --out Database --saves <saves dir>   # on Linux add --game-version <x.y>: the exe's version resource is read on Windows only
dotnet build RelicWriter.slnx
```

The Extractor takes the previous data from the migrations compiled into it (build after every run; it refuses to run if the `Database/` folder and its build disagree), reads the game's TweakDB and text, and writes a migration only if something changed. Seed lists it starts from are in `RelicWriter.Extractor/Seeds/`: the enum defaults (from the game's type information), the record names (from CP2077SaveEditor and CyberCAT, both MIT), the vehicle list, and the perk list with maximum levels (see `game-data.md`). Add the new `.sql` to the `Database` folder of `RelicWriter.slnx`.

The data contains text from the game (item, vehicle and perk names), CD PROJEKT RED's; check redistribution before publishing a build.

## Not done

- No downloader. A later update only has to get a new migration (SQL script and class) into the app; how that arrives is undesigned. EF migrations are compiled in, so a download of a bare script would need a loader for scripts that have no class.
- Removed or renamed game records are never deleted, only replaced; there is no "since game version" column.
- The Relic perk data and prerequisites are as described in `game-data.md`.
